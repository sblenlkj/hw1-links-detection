# Law Links Detector

Сервис для выделения юридических ссылок из русского текста. Проект выполнен в рамках группового задания №1 по NLP.

## Как мы понимаем задачу

На вход сервис получает произвольный текст. В тексте необходимо найти ссылки на конкретные нормы права и представить каждую найденную норму как `LawLink`:

```json
{
  "law_id": 1,
  "article": "12",
  "point_article": "1",
  "subpoint_article": "б"
}
```

`law_id` должен соответствовать документу из предоставленного `law_aliases.json`. Статья, пункт/часть и подпункт извлекаются из текста ссылки.

Если одна текстовая конструкция содержит несколько структурных элементов, сейчас мы трактуем её как несколько отдельных ссылок. Например, `пп. 1, 2, 3 п. 2 ст. 3 НК РФ` превращается в три `LawLink`.

Если конкретный документ нельзя однозначно определить и найдено несколько возможных `law_id`, resolver сохраняет такую ссылку как ambiguous. В публичном `POST /detect` все ambiguous candidates добавляются к обычным распознанным ссылкам: это сознательный выбор в пользу recall. Для отдельной диагностики неоднозначностей доступен `POST /detect-ambiguous`.

## Общая идея решения

Мы не пытаемся распознать юридическую ссылку одним большим регулярным выражением. Обработка разделена на несколько небольших этапов:

```text
text
  ↓
поиск локальных признаков
  ↓
сегментация потенциальных юридических ссылок
  ↓
определение конкретного документа
  ↓
извлечение структуры нормы
  ↓
LawLink[]
```

Сначала независимые стратегии находят статьи, пункты, подпункты, названия и семейства документов (`code`, `federal_law`, `presidential_decree` и т. д.). Затем близкие признаки объединяются в одну потенциальную ссылку, после чего resolver пытается определить конкретный `law_id`. На последнем этапе списки структурных элементов раскрываются в отдельные `LawLink`.

Подробное описание алгоритма и архитектуры находится в [docs/algorithm.md](docs/algorithm.md) и [docs/architecture_short.md](docs/architecture_short.md).

## API

FastAPI-сервис предоставляет:

- `POST /detect` — все найденные юридические ссылки: однозначные результаты плюс все candidates из ambiguous-ссылок;
- `POST /detect-ambiguous` — диагностическое представление ссылок, для которых найдено несколько возможных документов;
- `GET /health` — проверка доступности сервиса.

Swagger доступен по адресу `http://localhost:8978/docs`.

## Структура проекта

Папки разделены по назначению, чтобы отдельно держать исходные материалы, данные для проверки, реализацию и вспомогательные инструменты:

- `dataset/` — данные для проверки поведения детектора на текстах с известным ожидаемым результатом;
- `docs/` — отдельная техническая документация по алгоритму и архитектуре, чтобы не перегружать README;
- `hw_materials/` — исходные материалы и шаблон задания преподавателя, сохранённые как точка отсчёта;
- `law_aliases/` — подготовленное представление справочника юридических документов, которое использует resolver;
- `scripts/` — небольшие утилиты для ручного запуска и проверки сервиса;
- `smoke_tests/` — сценарии для быстрой ручной проверки отдельных этапов pipeline и целых примеров;
- `src/` — основной код приложения;
- `tests/` — автоматические тесты, запускаемые через pytest.

## Запуск

Локально сервис можно запустить через установленный CLI:

```bash
uv run links-detector
```

После запуска доступны:

- `http://localhost:8978/detect` — основной endpoint;
- `http://localhost:8978/health` — health check;
- `http://localhost:8978/docs` — Swagger UI.

Пример запроса:

```bash
curl -X POST "http://localhost:8978/detect" \
  -H "Content-Type: application/json" \
  -d '{"text":"Согласно пункту 2 статьи 5 Бюджетного кодекса Российской Федерации..."}'
```

## Тестирование

Базовая проверка перед изменениями — unit/regression suite. Перед сдачей наиболее полезно дополнительно прогнать generative black-box сценарий: он проверяет уже полный HTTP-путь на случайной выборке документов и структур.

### Unit и regression tests

Основная проверка выполняется через `pytest`:

```bash
uv run pytest --ignore=tests/performance
```

Отдельно в `tests/performance/` находится benchmark, который можно запускать при необходимости:

```bash
uv run pytest tests/performance
```

Тесты покрывают стратегии поиска структурных элементов, сегментацию, resolver по семействам документов, неоднозначные номера и названия, вложенные кавычки и разворачивание одной текстовой конструкции в несколько `LawLink`.

### Generative black-box test

Дополнительно в проекте есть black-box сценарий для проверки уже запущенного HTTP-сервиса на случайной сбалансированной выборке документов из `law_aliases`.

Сначала генерируются targets:

```bash
uv run python scripts/codex_generate_cases.py --runs 5 --references 3 --seed 42
```

Скрипт создаёт `.artifacts/codex_test_cases.json`: выборка балансируется по семействам документов и по типам структуры. Среди структур есть одиночные и множественные статьи, пункты, части, подпункты и комбинации нескольких пунктов с несколькими статьями.

Далее Codex, ChatGPT или другая LLM может прочитать `docs/codex_test_task.md` и на основе targets сгенерировать естественные фрагменты юридического текста в `.artifacts/codex_generated_texts.json`. Модель не получает право изменять код сервиса: её задача только корректно встроить заданные ссылки в текст.

После этого checker отправляет тексты в настоящий `POST /detect`:

```bash
uv run python scripts/codex_check_cases.py
```

Проверяется не только наличие нужного `law_id`, а полный кортеж:

```text
(law_id, article, point_article, subpoint_article)
```

Например, конструкция `пункты 2 и 4 статей 10 и 12` должна раскрыться в четыре отдельных `LawLink`. Ambiguous candidates считаются допустимыми результатами: публичный `/detect` сознательно ориентирован на recall и возвращает все возможные candidates.

Такой сценарий не заменяет unit tests, но хорошо дополняет их как интеграционная проверка полного пути `generated text → HTTP → FastAPI → parser → response`, в том числе для Docker-контейнера.

## Docker и публикация image

Приложение собирается в Docker image и запускается как FastAPI-сервис на порту `8978`.

Сборка и локальный запуск:

```bash
docker build -t law-links-detector:local .
docker run --rm -p 8978:8978 --name law-links-detector law-links-detector:local
```

Проверка контейнера:

```bash
curl http://localhost:8978/health
```

После этого те же black-box тесты можно запускать против Docker-контейнера без изменений: checker по умолчанию обращается к `http://127.0.0.1:8978/detect`.

Release workflow в GitHub Actions запускается при создании и отправке version tag вида `v*` (например, `v0.1.0`). Перед публикацией он запускает тесты, экспортирует production dependencies, собирает Docker image и проверяет, что контейнер успешно отвечает на `/health`.

После успешной проверки image публикуется в GitHub Container Registry с version tag и `latest`.
